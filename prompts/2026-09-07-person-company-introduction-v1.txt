==================================================
5. TOKEN SECURITY
==================================================

Generate:

32 random bytes

Store only:

SHA-256(token)

Raw token must never be stored in DB, logs or audit.

Expiry:

24 hours for DEV unless current policy specifies another sensible value.

Email link may carry raw token in URL fragment so it is not sent in the initial HTTP request.

Example conceptual link:

https://dev.samma.co.za/person/invitations#token=<raw-token>

Client should:

- read fragment
- clear it from browser history
- submit token only through same-origin POST

But:

the authenticated invitation inbox must NOT require the raw token.

Once SAMMA has authenticated the intended verified recipient, acceptance from the inbox can use:

invitation ID
+
CSRF
+
server-side recipient authorization

This is the preferred normal flow.

13. RELATIONSHIP ACCEPTANCE
==================================================

Accept in one safe transaction.

Rules:

If an ACTIVE relationship already exists:
- do not create duplicate
- mark invitation resolved appropriately/idempotently

- activate it

If no current relationship exists:
- create ACTIVE EMPLOYMENT relationship

If only FORMER/ENDED historical relationship exists:
- preserve history
- create a new ACTIVE relationship

Do not rewrite historical rows.
